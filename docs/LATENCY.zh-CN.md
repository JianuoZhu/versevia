## 已确认

1. 实际断句、翻译、对齐请求均省略 `reasoning_effort`。官方 [GPT-5.6 Luna 文档](https://developers.openai.com/api/docs/models/gpt-5.6-luna) 将默认值列为 medium，并支持 low 和 none。Chat Completions 的字段是顶层 `reasoning_effort`；降低它可能减少推理 token 和等待，但实际收益尚未测量。
2. 生产 content + background 的门控响应测试确认：冷启动长句要依次等待断句、整批翻译、该句的双语对齐三次响应。短句通常只需前两次。所有请求当前均非流式，当前句不能提前于整批响应完成显示译文。
3. 158 秒的合成字幕测试复现了额外取消：第一窗口完成后，并行发出第二个断句请求和 8 句翻译请求；若第二次断句先完成，`replaceTimeline` 调用 `resetTranslations`，取消尚未完成的 8 句翻译，然后把同样的 ID 重新发送。该例中翻译请求正文长度也完全相同。原因是更换整个 generation，而不是模型推理。本次尚未修复此调度缺陷。
4. 上一版首批从 2 句增加到最多 8 句，后续最多 48 句，增加吞吐和上下文的同时也可能提高当前批次的等待时间。48 句是上限，不是每次实际都会发送 48 句。尚无证据量化它在用户目标视频中的影响。

以上测试在本地拦截了网络，用人工指定的响应释放顺序验证因果；没有将本地执行毫秒数当作 OpenAI 服务耗时。复现命令：

```powershell
node scripts/probe-subtitle-latency.mjs
node scripts/probe-subtitle-latency.mjs --long
```

## 使用已有配置做真实对比

密钥保存在浏览器扩展的 `chrome.storage.local`，不在项目源码或终端环境中。本次没有读取浏览器配置数据库、导出密钥或创建新密钥。

1. 重新加载扩展，并重新打开 Providers 设置页，选择已有的 OpenAI 配置。
2. 暂停其他 YouTube 标签页里的字幕处理，减少竞争。
3. 点击 **Compare Luna latency · 6 paid requests**。无需再次保存服务配置。
4. 固定八句合成日文，用现有生产翻译提示测试 `default → low → none → none → low → default`。每种两次，不使用扩展翻译缓存。每请求最多 90 秒；错误停止后续请求。Stop 会等当前请求结束后停止。测试只支持官方端点上的已保存 GPT-5.6 Luna，不切换模型，不修改正常请求参数。
5. 页面保留 JSON 结果：完整响应耗时、响应头耗时、输入／输出／推理 token、服务端已缓存输入 token 和实际八句译文。可以复制结果供分析，不含密钥、当前视频内容或个人字幕。

两次样本只是初步对比，服务端缓存、网络和负载仍会影响结论；响应头时间也不等同于首 token 时间。需要同时比较译文质量，不能只凭速度选择 none。该入口只测八句翻译，不能代替断句质量评估、48 句批次测试或整条播放链路的实时延迟测量。

建议后续先修复不必要的取消和重发，再根据真实对比决定翻译使用 none 还是 low；断句及对齐可单独评估 low 的质量，不应未经测试全部关闭推理。保留较大的后台预取批次，另外控制当前播放位置的首屏等待。
